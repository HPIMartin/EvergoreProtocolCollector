| **D18** | **Pre-group the recompute's aggregation in SQL instead of loading every row into the JVM** (author proposal 2026-09-03, measured the same day): the evaluator loads all of an avatar's entries as objects and values them one by one, so both memory and time grow linearly with the log forever, the OOM path once the ledgers outgrow the heap. The valuation is **linear** in `quantity × quality`, so it factors exactly: `Σ storageValue(item) · quantity · quality/100 = storageValue(item)/100 · Σ(quantity · quality)`. A `GROUP BY avatar, name, type` with `SUM(quantity * quality)` therefore loses **nothing** and needs no `quality` in the key. Measured on the production snapshot: **4,510** storage groups and **47** bank groups instead of 245,072 rows (54× fewer), the whole guild in one statement in **~160 ms**, and the integer sums stay exact (largest group 225,941,200, far from int64).
